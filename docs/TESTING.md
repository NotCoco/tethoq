### Real-provider findings recorded from the live server

- `clientUserMessageId` on `turn/start` is a correlation id, not an idempotency key: repeating
  `turn/start` with the same id started a second turn. The Agent Bridge `RequestLedger` is
  therefore the real send-idempotency boundary; it is in-memory per bridge process.
- Threads created by one app-server process cannot be deleted from another process while the
  owner holds the rollout writer ("already has an active writer"). Cleanup must run through
  the owning connection.
- The installed runtime returns extra Thread fields (`extra`, `historyMode`,
  `canAcceptDirectInput`) not present in `generate-ts` output; the adapter preserves them as
  opaque native metadata.

### Shared Node/Dart vectors

`packages/protocol/test_vectors/` contains canonical-JSON, host-signed credential, and
device-signed action vectors generated by the Node reference implementation with the RFC 8032
Ed25519 test keys. Both sides pass the same vectors:

- Node: `packages/protocol/src/vectors.test.ts` (byte-match, credential verify, action verify
  + tamper rejection).
- Dart: `apps/remote_client/test/vectors_test.dart` (same vectors, plus rejected-value
  throws).

This proves cross-language compatibility for the signing pipeline: Node-signed credentials and
actions verify under the Flutter client, and Dart `canonicalJson` byte-matches Node
`canonicalizeJson` on the shared inputs.

- Collision-safe global session ID round trip, including separators and Unicode.
- Runtime envelope validation and protocol-version rejection.
- Context-handoff/branch request trimming, empty-prompt rejection, and the
  32,000-character prompt limit.
- Published protocol JSON Schema parses and tracks v1.
- Approval and user-input response validation.
- Event deduplication and bounded replay sequencing.
- Exponential reconnect backoff bounds/reset.
- Pairing secret confirmation and idempotent retry.
- Host-signed device credential verification.
- Expiring device action signature verification.

- Persisted revocation across bridge restart.

### Refresh and bridge

- Complete multi-page refresh.
- Cursor-loop rejection.
- Partial provider failure preserves successful data and marks failed-provider cache stale.
- Fake provider end-to-end flow:

```text
connect host
-> list/refresh sessions
-> open session
-> stream response
-> tool + command events
-> receive approval
-> approve
-> continue stream
-> complete
```

- User-input request normalization and exact provider response binding.
- Duplicate provider event suppression with out-of-order unique event retention.
- Request ID deduplication across independent connection routers.
- Provider model enumeration route without invented models.
- Deterministic 100-1000 word handoff summaries, fresh-session enforcement,
  visible top-level summary metadata, and exactly-once first-send bootstrap.

  normalized-transcript fallback with private reasoning/binary payload omission.
- Failed first-send retry, branch-of-branch history, restart restoration from
  `session-transfers.json`, and sanitized persisted branch copies.
- Large inline history images replaced with an opaque retrieval ID and rebuilt
  byte-for-byte through bounded authenticated chunks.

### Codex adapter (deterministic, added this run)

- Command execution and file-change approval responses use `{ decision: accept|decline }`.
- Legacy `applyPatchApproval`/`execCommandApproval` responses use `ReviewDecision`
  (`approved` / `{ denied: { rejection } }`).
- `item/permissions/requestApproval` responds with a granted profile and `scope: "turn"`;
  rejecting grants an empty profile (the schema has no decline case; session-wide grants are
  never invented).
- User-input answers normalize into `{ [questionId]: { answers: string[] } }`.
- Unsupported server requests (for example `attestation/generate`) produce an explicit error
  response rather than a fake success.
- History normalization covers real ThreadItem shapes: `mcpToolCall`, `dynamicToolCall`,
  `collabAgentToolCall`, `webSearch`, `fileChange` change arrays, `commandExecution`
  `inProgress`/`declined` statuses.

- Real Codex approval, user-input request, and turn interrupt were not triggered live (the
  local sandbox config did not produce a permission boundary crossing). The response mapping
  is covered by deterministic adapter tests against the generated schema.
- Building/running the native Windows Flutter app (requires Developer Mode for plugin
  symlinks, unavailable in this non-elevated session) and any iOS/macOS/Linux build.
- `opencode` and `grok` executables were not installed.
- No live Direct API model turn, key validation, or billable request was run.
- TLS relay, QR camera pairing, multi-device/multi-host UI, iOS/macOS behavior, and extended
  Android lifecycle/network-handoff interaction. The Android debug APK was installed in place
  and launched successfully on a physical Android 16 device.

## Test honesty rule

A source fixture passing means the normalizer handled that recorded shape. The opt-in Codex
tests passing means the installed Codex accepted those requests and returned matching shapes.
It still does not mean every provider feature or every user account was exercised. Build
status distinguishes `COMPLETE`, `IMPLEMENTED_UNTESTED`, `PARTIAL`, and local blockers
accordingly.
